# 当前桌面的窗口清单、画面与点击

## 复现

旧安装版 5.21（82）的正式侧栏曾同时显示 7 张卡。独立观察器在同一普通桌面上找到了 4 扇有普通 AX 身份且在屏的窗口。另外 3 个记录在当前和全空间 AppKit 排序中均已消失，CG 报告不在屏，AX 也没有对应的普通窗口。旧版仅凭 Space 归属就保留了它们。两扇新建文档的对照实验还复现了原应用执行 `orderOut` 后卡片残留。上述检查未读取个人窗口标题或像素。

## 修复

窗口清单、点击和缩略图共同验证当前显示器与桌面。对有 AX 证据的普通窗口检查最小化、模态和角色；被普通窗口遮住仍可保留。build 84 的现场复核发现，即使 AppKit 和 CG 同时报告当前可见，7 张卡里仍混入一张普通层级的辅助面板。最终版要求逐窗确认普通角色与未最小化状态。无法核对角色时，侧栏显示权限或状态说明，不为该表面画卡片或创建点击目标。原已授权的自动平铺仍走独立的窗口身份、权限和写入检查。

图片缓存和异步取图都绑定进程启动身份、窗口编号及本次窗口生命周期。点击时核对原目标；应用若暴露唯一窗口编号，Host 可以直接校验 AX 目标、几何和最终焦点。其余情况沿用原有独立助手。测试控制器改用独立 Bundle ID，正式安装版继续沿用同一个 Developer ID 签名。

## 为什么权限开着仍然失败

在本机正式 Host 的即时权限读数中，屏幕录制与辅助功能均返回未获准。macOS 的 `tccd` 对安装在 `/Applications/Nearpane.app` 的身份分别报告 `Failed to match existing code requirement`。屏幕录制和辅助功能的既有记录各自要求一个旧签名哈希；两者也不相同。系统界面里的同名开关不能证明当前可执行文件满足旧记录。此前反复提示“打开开关”遗漏了这个区别。

权限说明现在能直接定位当前安装包，并解释旧签名授权的处理方法。只有账户所有者能在系统允许的授权界面把两项记录重新绑定到当前签名。本轮未重置权限、未更改系统开关，也未把验收工具的权限借给产品。


## 实拍复审

在具备自身取图权限的隔离进程中，我核对了实际产品侧栏视图的局部实拍。测试只向该视图提供两款自建应用的窗口。

- 可在各桌面显示的四扇普通文档窗，其绿、蓝、橙、红画面逐一对应，横竖及大小关系保留。关闭蓝窗、撤下橙窗后只剩绿、红两张，已移除两种测试色的像素数均为 0。
- 同一机器的常规台前调度文档场景出现了实际失败。三个窗口均能列出，只有橙窗取得完整图像，两扇 Notes 窗是轮廓。所有者报告的逻辑尺寸为 520 × 175 与 230 × 340 pt，系统取图过滤器给出 199 × 129 与 60 × 113 pt。使用该窗口的原始配置、指定尺寸以及传统单窗截图接口均返回 ScreenCaptureKit 错误 −3811。该系统构建的这两扇窗口上尚未取得可验证的完整内容。
- 上述取图仅用于验收合成文档。最终安装版必须自行获得系统授权；隔离进程的图像没有进入产品。收据仅提交计数和状态，原始 PNG 留在本机的 Git 忽略目录。
