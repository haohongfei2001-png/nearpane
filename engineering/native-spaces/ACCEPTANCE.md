## 1. 验收主体

实际执行者必须是**最终安装的 Nearpane**，通过生产侧栏和生产动作服务完成操作。验收器仅准备受控目标、投递真实点击/拖动、独立观察及记录；不得替产品执行切空间/迁窗，也不得在另一个已授权进程加载生产 UI 后冒称交付版通过。

分三层记录：单元/模拟回归；真实系统受控目标；最终安装应用端到端。三层互相补充，不能互相代替。

每轮冻结 manifest：source SHA、版本/build、安装路径、bundle ID、Host/helper SHA-256 与 CDHash/Team ID、OS version/build、CPU 架构、SIP 状态、显示器 UUID/几何/旋转/缩放、独立 Spaces 开关、Stage Manager 状态、实际产品权限与后端 pin。

原生基线可用自建 AppKit 窗口；兼容验收必须包含实际应用。只使用临时文档、临时目录、本地页面或独立空白浏览器配置，不发送网络消息、不操纵私人文档、不清空用户会话。

## 3. 原生体验对照与性能

在同机、同拓扑、同批测试内容、同系统设置下，采集至少 20 次系统原生参考操作，再采 Nearpane。分开记录冷启动和预热；全部样本保留，不选最好一次。

以单调时钟记录：
- t0：用户点击/拖放意图进入产品；
- tFeedback：首次可见反馈；
- tIssued：系统动作投递；
- tArrival：系统目标 Space 确认；
- tInput：具体目标窗实际接收输入（只有选窗场景适用）。

验收目标：

| 指标 | 目标与判定 |
| --- | --- |
| 首次反馈 | P95 ≤ 100 ms；UI 不因 helper/AX/SCK 阻塞 |
| 相同动画策略的到达且可输入 | P95 比同机同场景原生参考增加 ≤ 150 ms；Space-only 用 tArrival，选窗用 tInput |
| 空间状态同步 | 系统稳定后侧栏 current/成员更新 ≤ 500 ms |
| 初次可捕获窗口画面 | 普通可捕获测试窗 P95 ≤ 1 s；不可捕获内容单独分类，不无限等待 |
| 稳态开销 | 按下述固定协议验证：隐藏后停止像素捕获；缓存有硬上限；重复同一操作批次后内存回到规定容差内；保留 Host+helpers 的全部原始计数 |
| 动效质量 | 默认平滑连贯，遵循减少动态效果；无黑帧/旧桌面闪回/过冲/非相邻明显逐段闪过，Nearpane 表面无意外抢焦点 |

**稳态开销固定协议（本轮新增工程预算，不是已测成绩）：**

1. 固定测试窗口、Space 数量和其他模块状态。所有空间预览及其悬浮预览隐藏/停用后，2 s 内停止新的像素捕获请求及活动捕获流；随后观察 60 s，新增捕获帧计数为 0。允许保留必要的系统状态通知与有界元数据核对。
2. 缩略图像素缓存必须实现并记录硬上限：最多 128 个窗口的缓存画面，全部像素缓存总计最多 256 MiB（包含解码副本；采用较先达到的限制），超出后按 LRU 回收。元数据库存不随缓存淘汰删除；画面按实际显示分辨率降采样。不可把缓存丢失伪装成窗口消失。
3. 对同一组窗口和 Space 先完成一批 20 次操作并预热；静置 30 s，记录 Host 与 helpers 的进程树物理内存基线。随后重复 5 批相同的 20 次操作，每批静置 30 s 后再次记录进程树内存、缓存条目、像素字节和活动流数。每次静置后的内存应不高于预热基线加 `max(64 MiB, 基线的 10%)`，且缓存始终满足硬上限。
4. 保留每个样本与测量方法；若进程发生重启，不能把重启后的低内存当作回收成功。未实现计数或未运行协议，稳态开销保持 NOT_RUN；超限则定位并修复，不能凭一次资源监视器截图判 PASS。

ISS 瞬切与系统默认动画不能混用相对耗时比较。只有瞬切成功时，“原生式默认动效”仍不通过。允许内部实现不同于 Apple，但用户可见结果须满足上表；不用虚构精确相同的系统动画。

使用实际录屏与逐帧检查判定明显视觉缺陷，并保存原生参考与 Nearpane 对照片段。测试画面必须只包含获准的合成内容。不能用 HTML 原型、离屏渲染或效果图替代真实 WindowServer 画面。

目标未达到则定位、修复和复测；不得事后静默放宽阈值。确需改变合同，记录工程证据和明确的未达项，不能由执行者为了变绿直接改成 PASS。

## 4. 自动化与证据产物

Codex 应实现一条工程验收入口（建议 `scripts/acceptance/native-spaces/run.sh`），及支持预检、场景选择、汇总、清理的可重跑流程。该路径是待创建的交付要求，本计划没有声称它已存在或执行。

用实际 App UI 发起动作。内部系统读数可以用于独立观察；测试专用“直接切空间”接口只能作后端开发测试，不能代替用户场景通过。

每轮生成：
- `manifest.json`：环境、安装/签名、源与依赖 pin；
- `actions.jsonl`：意图 ID、目标身份、before、投递、after、独立焦点/输入证据、耗时、判定；
- `results.json` 与简短 `RESULTS.md`：每场景 PASS/FAIL/BLOCKED/NOT_RUN、总尝试/失败/未知数、性能分位数；
- 少量真实截图和短录屏：普通切换、跨 Space 精确选窗、拖窗、空 Space、全屏/多屏和原生动效对照；
- 清理结果：测试窗口/文件/空间的去向、仍保留的用户对象、最终状态。

将决定准入的脱敏摘要、关键 JSON 和媒体清单写入版本化目录 `engineering/verification/native-spaces/<run-id>/`，大文件可放可访问的 CI/Release artifact 并记录哈希和有效链接。不能只链接被 gitignore 的本机 build 目录。测试原始数据保留失败样本，合成内容与个人画面严格区分。

## 5. 真正的通过标准

本轮必验集合在开工前固定：核心功能通过需要 S01–S03、W01–W03、V01、D01、R01、P01、I01 全部通过；默认体验还必须 N01 通过。整体空间/窗口专项完成还需要 L01/L02/C01/F01/M01/R02 全部通过。

后端未实现、缺设备、缺权限或当前路线不支持，只能记录 FAIL/BLOCKED/NOT_RUN，专项保持 PARTIAL；不得由执行者删除必验场景或改为“不适用”后宣布完成。N/A 仅用于场景内部客观不适用的单条判据（例如空 Space 不要求 key window），必须写明理由，不能把整个必验场景排除。

所有完成的样本中，错误 Space、错误窗口、错误屏幕、错动兄弟窗、窗口丢失/不可访问、虚假成功均须为零。发生一例就修复并重测该场景与受影响核心，不能从统计中删除。

- 单元测试/CI、效果图、隔离 UI 成功、API true、发送事件、应用 PID 前台均不是独立通过依据。
- 不允许把功能关掉、变只读、换成 Virtual 或让用户手动切空间后再截图来完成验收。
- BLOCKED/NOT_RUN 不计入 PASS；环境缺失可保留受限候选，但任务保持 PARTIAL，不宣称完整达标。
- 核心成功不被创建/删除尚未完成抹去；同时不能因此关闭全部任务或宣称原有扩展规则已兑现。
- 实际支持范围明确到 macOS build/架构和已测模式；未来系统兼容不预先承诺。
- 首次系统权限确认是可能无法代办的环境动作，不能把后续测试、协调或视觉判断整包推给用户。

## 6. 测试环境与恢复

使用自建可控窗口作为基线，同时用实际应用的全新临时内容做兼容。不关闭用户已有窗口，不丢未保存内容，不删除用户原有 Space，不静默注销、关闭 SIP 或修改 TCC。

准备与清理可调用工程工具，须与正式产品动作分开计数。恢复测试前状态时只处理本次测试对象；用户途中产生新操作时停止迟到的恢复，不强抢回旧焦点。

独立 Spaces 开关若需注销生效，在独立可控会话/设备完成该组合。缺少第二显示器或相关系统组合时，先完成其余真实验收，准确标出缺项；不能用模型或假显示器截图称物理多屏 PASS。

## 7. 最终交付内容

一个可运行的 Nearpane 候选、实现 PR、当前能力与支持矩阵、上述实机结果、可重跑入口、简短实际演示、回退方法及剩余真实阻塞。Codex 的最终回复应说明“用户现在能完成什么操作”和证据，而非只汇报新增多少测试。


### W01 同桌面双文档

在已有空普通桌面的所有权收据下，使用正式安装、已绑定隔离资料的 Nearpane 侧栏。为独立文档 App 和读取器编译同团队 Developer ID 工具包。正式候选无需重新编译。

```sh
src=scripts/acceptance/native-spaces
document_kit=$(mktemp -d /private/tmp/nearpane-d01.p2-documents.XXXXXXXX)
"$src/build-marker-witness.sh" "$document_kit" --registered-documents
NP_P2_DOCUMENT_KIT="$document_kit" python3 "$src/installed_profile.py" --p0-focus-kit "$full_kit" "$output/profile" -- \
  python3 "$src/preview-on-lease.py" "$full_kit" "$workspace" "$output/native" \
    --expected-space "$space_id" --scenario controlled-window \
    --previous-archive "$previous_archive" --install-receipt "$install_receipt" --original-checkout "$checkout"
```

`full_kit`、`workspace`、`space_id` 和最后三个参数沿用同一已登记租约的入口，`output` 为新的输出目录。Launch Services 在后台新开同一 App 的两个普通文件窗。签名、进程生辰、两个 AXDocument/CGID 和每个编辑器均与夹具绑定后才允许向正式侧栏发起选窗。每轮标记随机，单次定向投递，前后连续两次交叉检查两个文件的 AX、AppKit 和落盘摘要。首次不一致即终止后续试次。新的物理按键、点击或拖动会使验收标记为 `userSuperseded` 并释放焦点。若用户停留在夹具内，夹具等失去前台后才关闭。

`native/controlled-window/registered-documents.json` 记录 10 次是否完成、签名、登记身份与清理。`actions.jsonl` 记录每个意图、真实 AXPress 和定向事件是否已发出，以及两份文件各自的独立读回。`marker-witness-NN.json` 记录该随机标记的 AppKit 事件来源。`profile/profile-session.json` 记录日常资料恢复；夹具准备、正式 Host 选窗和其他应用的覆盖分别判定。
